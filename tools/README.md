
# MedOrbits Repository Reports

**Directory:** `tools/repository-reports/`

## 1. Purpose

This directory stores machine-readable reports generated by MedOrbits repository auditing tools.

Reports help identify:

- Broken references and unresolved file paths.
- API route declarations and references.
- Duplicate files, identifiers, and content.
- Merge conflict markers.
- Dependency relationships.
- Page connection and navigation opportunities.
- Parsing warnings and repository integrity issues.
- Overall repository health and audit summaries.

Reports are diagnostic artifacts. They do not automatically authorize source-code changes, file deletion, route changes, or dependency upgrades.

> **Important:** A report template is not evidence of a completed scan. Findings must be generated from the actual repository and verified before remediation.

## 2. Directory Structure

The following is the intended report layout. A file is considered available only when it exists in the repository.

```text
tools/
└── repository-reports/
    ├── README.md
    ├── api-routes.json
    ├── broken-references.csv
    ├── broken-references.json
    ├── conflict-markers.json
    ├── dependency-edges.csv
    ├── parse-warnings.json
    ├── references.json
    ├── summary.json
    ├── unresolved-references.json
    └── page-connection-suggestions.json
```

Additional reports may be added as auditing capabilities expand.

## 3. Report Reference

| Report | Purpose |
| — | — |
| `summary.json` | Aggregated repository audit results and issue counts. |
| `api-routes.json` | Discovered API route declarations and associated metadata. |
| `references.json` | References discovered across scanned repository files. |
| `broken-references.json` | Structured records of verified broken local references. |
| `broken-references.csv` | Spreadsheet-friendly export of broken-reference findings. |
| `unresolved-references.json` | References that remain unresolved or require verification. |
| `page-connection-suggestions.json` | Suggested internal links, navigation improvements, and potential orphan-page connections. |
| `conflict-markers.json` | Git merge conflict markers discovered in scanned files. |
| `dependency-edges.csv` | Relationships between files, modules, and dependencies. |
| `parse-warnings.json` | Files or constructs that could not be parsed reliably. |

The presence of a report in this table does not establish that the file exists or has current findings.

## 4. Report Status and Freshness

Each report should communicate its provenance and processing state.

Recommended metadata:

- `reportVersion`: version of the report structure.
- `reportType`: stable report identifier.
- `repository`: repository name or identifier.
- `generatedAt`: generation timestamp in ISO 8601 UTC format.
- `status`: processing status.
- `summary`: aggregate counts derived from the report records.

Suggested statuses:

| Status | Meaning |
| — | — |
| `pending_scan` | The report has not yet been populated by a scan. |
| `running` | The audit is in progress. |
| `completed` | The scan completed successfully. |
| `completed_with_warnings` | The scan completed with warnings or incomplete coverage. |
| `failed` | The scan failed before producing a complete report. |
| `stale` | The report no longer represents the current repository state. |

Use `null` for unknown timestamps or metadata. Do not invent scan results, timestamps, or findings.

## 5. Reference Audit

Reference audits should discover and classify references before determining whether they are broken.

Common reference categories include:

- HTML links and navigation targets.
- Images, icons, fonts, and downloadable assets.
- CSS imports and `url(...)` resources.
- JavaScript imports and module references.
- API routes and endpoint references.
- JSON schemas and configuration references.
- GitHub Actions workflow paths.
- Documentation links and internal page references.

### Resolution rules

1. Preserve the original reference exactly as found.
2. Record the source file and line number when available.
3. Resolve relative paths against the correct source directory or runtime base.
4. Normalize paths safely without escaping the repository root.
5. Account for case sensitivity on the target deployment platform.
6. Distinguish local files, external URLs, fragments, aliases, and runtime-generated paths.
7. Treat dynamic or ambiguous references as unresolved until additional checks are possible.
8. Do not classify an external URL as broken solely because the scanner is offline.
9. Avoid following symbolic links outside the permitted repository boundary.
10. Preserve query strings and fragments when evaluating links.

A failed automated lookup is not always proof that a reference is invalid.

## 6. API Route Reports

API route reports should capture, where available:

- HTTP method.
- Route path or route pattern.
- Source file and line number.
- Router or controller association.
- Middleware and authentication requirements.
- Route registration status.
- Potential duplicate declarations.
- Unresolved controller or handler references.

Route discovery must account for mounted routers, prefixes, dynamic parameters, and framework-specific routing behavior.

Do not assume a route is missing merely because its path is not declared in the same file as its caller.

## 7. Conflict Marker Reports

Conflict-marker audits should identify unresolved Git conflict blocks, including:

```text
<<<<<<<
=======
>>>>>>>
```

A scan should record the file, line number, marker type, and surrounding context when available.

Important safeguards:

- Do not automatically remove conflict markers without reviewing the affected content.
- Distinguish actual merge conflicts from intentional examples in documentation, fixtures, or tests.
- Preserve new and untracked files.
- Inspect staged and unstaged changes before attempting repairs.
- Create a backup or checkpoint before destructive Git operations.
- Never use a blanket checkout, reset, clean, or revert operation as an unreviewed conflict-resolution strategy.

## 8. Dependency Relationship Reports

Dependency edges describe relationships such as:

- Source file to imported module.
- HTML page to referenced asset.
- CSS file to imported stylesheet or font.
- Workflow to invoked script.
- API route to controller or service.
- Configuration file to schema.

Recommended CSV columns:

```csv
source,target,relationship,source_line,status
```

Use repository-relative paths where practical. Record external dependencies separately from local files.

A dependency edge is a discovered relationship, not necessarily a runtime execution path.

## 9. Page Connection Suggestions

`page-connection-suggestions.json` supports review of internal navigation and related-content opportunities.

Suggestions may include:

- Missing links from category pages to relevant child pages.
- Relevant contextual links between related educational pages.
- Breadcrumb or parent-page opportunities.
- Career and admissions journey connections.
- Potentially orphaned pages.
- Related support and documentation links.

Before approving a suggestion:

1. Confirm that the target page exists.
2. Verify that the target is intended for public access.
3. Confirm semantic relevance to the source page.
4. Check for duplicate or self-referential links.
5. Use descriptive anchor text.
6. Consider accessibility, canonical URLs, and navigation consistency.
7. Review the suggestion manually when confidence is low.

Do not automatically publish private files, internal reports, source code, or repository documentation as public website links.

## 10. Severity and Confidence

Severity describes potential impact; confidence describes how strongly the evidence supports a finding. They should not be treated as interchangeable.

Recommended severity levels:

| Severity | Guidance |
| — | — |
| `critical` | A verified issue with severe security, data integrity, or core-service impact. |
| `high` | A major defect or substantial risk affecting important functionality. |
| `medium` | A meaningful defect with limited scope or a viable workaround. |
| `low` | A minor defect or limited usability issue. |
| `informational` | An observation or improvement opportunity without a demonstrated defect. |

Recommended confidence levels:

- `high`: Supported by direct, reproducible evidence.
- `medium`: Supported by evidence but dependent on assumptions or incomplete context.
- `low`: A heuristic suggestion requiring further verification.

Do not assign severity based solely on a filename, a missing search result, or a speculative suggestion.

## 11. Recommended Audit Workflow

Run audits in a controlled sequence:

1. Inspect the repository and identify the actual audit scripts.
2. Confirm the working tree and preserve existing changes.
3. Run syntax and parsing checks.
4. Discover files and references.
5. Generate reference, route, dependency, and conflict reports.
6. Validate unresolved references and distinguish genuine defects from false positives.
7. Generate page-connection suggestions.
8. Recalculate report summary counts from the final records.
9. Validate JSON and CSV output formats.
10. Review high-impact findings manually.
11. Apply fixes in small, reviewable batches.
12. Rerun relevant audits and compare results.

Example commands, when the corresponding scripts exist:

```sh
git status —short

find tools/repository-reports -maxdepth 1 -type f -print

python -m json.tool \
  tools/repository-reports/unresolved-references.json \
  >/dev/null
```

The commands above inspect the working tree, list existing reports, and validate one JSON file. They do not generate audit findings or repair repository files.

Use the actual script names and documented options available in the repository. Do not assume a report-generation command exists until its implementation has been verified.

## 12. Validation Requirements

Before accepting generated reports, check the following:

- [ ] JSON files parse successfully.
- [ ] CSV files have consistent headers and row structure.
- [ ] Report types and versions are documented.
- [ ] Summary counts match the associated records.
- [ ] Finding identifiers are unique within the report.
- [ ] Source paths and line numbers are valid when provided.
- [ ] Placeholder examples are not counted as actual findings.
- [ ] Duplicate findings are identified or deduplicated.
- [ ] Unresolved and manually reviewed references are distinguished.
- [ ] Timestamps and repository revision metadata are accurate.
- [ ] Sensitive values and secrets are not included in reports.
- [ ] Generated reports do not silently overwrite source files.

## 13. Data Integrity and Security

Repository reports can contain internal paths, endpoint names, configuration details, and other operational metadata.

Follow these safeguards:

- Never include passwords, API tokens, private keys, session cookies, or other secrets.
- Avoid storing personal information or private application data in report records.
- Sanitize command output and error messages before including them.
- Keep public reports free of sensitive vulnerability details.
- Do not treat report contents as trusted instructions or executable commands.
- Review proposed file changes before committing them.
- Use private vulnerability reporting for sensitive security findings.
- Do not expose internal repository paths through public website navigation unless explicitly intended.

## 14. CI Integration

Repository reports can be generated during continuous integration to detect regressions.

A recommended CI workflow should:

1. Check out the intended commit.
2. Install only the required audit dependencies.
3. Run deterministic repository scans.
4. Validate the generated report formats.
5. Compare findings against an agreed baseline where appropriate.
6. Fail on explicitly configured blocking conditions.
7. Publish reports as artifacts when useful.
8. Avoid committing generated changes automatically without a defined policy.

Use explicit thresholds for blocking failures. Informational suggestions should not fail a build unless project policy requires it.

Do not print secrets or sensitive report contents to CI logs.

## 15. Report Maintenance

When report schemas change:

- Increment the report version when compatibility is affected.
- Document renamed or removed fields.
- Update the generating tool and consumers together.
- Preserve stable field names where possible.
- Regenerate reports rather than manually inventing findings.
- Mark stale reports clearly.
- Keep generated output separate from source-of-truth configuration.

## 16. Completion Criteria

A repository audit is complete only when:

- The intended repository scope has been scanned.
- The scanner’s coverage and limitations are documented.
- Reports have been generated from actual repository data.
- Report structures have been validated.
- Summary counts match the recorded findings.
- High-impact findings have been reviewed.
- Any remaining unresolved items are clearly identified.
- The generated artifacts correspond to the recorded repository revision.
