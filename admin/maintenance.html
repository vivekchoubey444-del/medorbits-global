Maintenance scheduling

Prepare a controlled maintenance request. Scheduling and maintenance activation remain unavailable until the authorised backend explicitly supports these operations.

Backend integration required.
These controls are disabled by default. The server must validate the requested schedule, check permissions, handle timezone conversion and record the result before any maintenance window is considered active.
The server must enforce permissions for each action separately.
Available scopes must be supported and enforced by the backend.
Use the approved maintenance window and verify the server timezone.
The end time must be later than the start time.
Do not include credentials, private incident details or personal information.
Provide an auditable reason for the requested operational change.

Operational readiness checklist

Use these checks before authorising a maintenance window.

01
Confirm scope and dependencies

Identify affected services, upstream dependencies, background jobs, integrations and user-facing workflows.

02
Prepare recovery and rollback

Validate backups where relevant, define recovery steps, assign an owner and establish a way to verify service restoration.

03
Communicate service impact

Publish accurate maintenance times and user guidance through approved channels. Avoid promising an unverified recovery time.

04
Record and review the change

Log the authenticated actor, approved reason, requested scope, timestamps, outcome and recovery confirmation without exposing secrets.

Infrastructure governance

Planned maintenance. Trusted recovery.

Keep platform changes controlled, service status observable and user communication accurate. Verify the real operational state before announcing downtime or successful recovery.

Security and availability notice: This page is an administrative client, not a security boundary.
