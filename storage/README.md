
# MedOrbits — Private Runtime Storage

**Directory:** `storage/`

## 1. Overview

The `storage/` directory is intended for private runtime files uploaded, processed, or generated by the MedOrbits application.

It may contain user documents, admission application attachments, employer verification records, generated reports, exports, temporary files, and other sensitive artifacts.

**Security principle:** Storage contents are not public website assets. Never expose this directory through unrestricted static-file serving or rely on obscure filenames as an access-control mechanism.

## 2. Directory Structure

```text
storage/
├── .gitignore
├── .gitkeep
├── README.md
├── tmp/
├── uploads/
├── documents/
├── applications/
├── profiles/
├── employer-documents/
├── generated/
├── exports/
├── quarantine/
└── backups/
```

| Directory | Intended purpose |
|—|—|
| `tmp/` | Temporary processing files and intermediate artifacts. |
| `uploads/` | Incoming files awaiting classification and validation. |
| `documents/` | Private user documents. |
| `applications/` | Admission application attachments. |
| `profiles/` | Profile images and user assets. |
| `employer-documents/` | Employer verification documents. |
| `generated/` | Generated reports, receipts, and PDFs. |
| `exports/` | Authorized data exports. |
| `quarantine/` | Files isolated pending security review. |
| `backups/` | Reserved for protected local backup workflows. |

The directory structure documents intended storage responsibilities; it does not imply that each workflow is implemented or secured.

## 3. Security Requirements

### 3.1 Private Access

- Never expose the storage directory through unrestricted `express.static()`.
- Authorize every document access and download on the server.
- Verify resource ownership, permissions, and applicable organizational access rules.
- Use private object storage for sensitive production files where appropriate.
- Do not use unguessable filenames or URLs as substitutes for authorization.
- Avoid returning physical filesystem paths or internal storage keys to clients.

### 3.2 Upload Validation

Before accepting or making a file available:

1. Enforce request-size, file-size, and file-count limits.
2. Allow only file types required by the relevant workflow.
3. Validate extensions, declared MIME types, and actual file signatures.
4. Generate opaque storage filenames on the server.
5. Prevent path traversal and unsafe filesystem operations.
6. Scan files for malware where required.
7. Keep unvalidated files isolated in quarantine.
8. Publish or expose a file only after the required validation and security checks succeed.

Client-supplied filenames, extensions, MIME types, and paths must not be trusted.

### 3.3 Quarantine

Files awaiting validation or malware scanning must remain inaccessible to ordinary users and public endpoints.

The application should track processing state explicitly, prevent downloads before approval, and define procedures for failed scans, rejected files, and manual review.

A file’s presence in `quarantine/` must not be treated as proof that it is safe.

### 3.4 Sensitive Information

Never use this directory as a general-purpose location for:

- Passwords or authentication secrets.
- API keys, signing keys, or access tokens.
- Payment card data or payment credentials.
- Unrestricted database dumps.
- Unencrypted confidential exports.
- Files that should be stored in an approved secrets manager or secure payment system.

Encrypt sensitive data in transit and at rest. Protect encryption keys separately from the data they protect.

## 4. Production Storage Architecture

For production deployments, private object storage is generally preferable for sensitive documents when practical.

A recommended application flow is:

```text
Upload
  → Validation
  → Quarantine
  → Security Scanning
  → Private Storage
  → Database Metadata
  → Authorized Access
```

The database should store the validated metadata required by the application, such as:

- Opaque file identifier.
- Related user, application, or employer identifier.
- Storage key or object identifier.
- Validated file type and size.
- Processing and security-review status.
- Creation timestamp and applicable retention information.

Store only the metadata required for the workflow. Avoid duplicating sensitive file contents in database records.

Use short-lived signed download URLs only when appropriate, and issue them after authorization. Keep private buckets and objects inaccessible to anonymous users.

## 5. Retention and Deletion

Define retention requirements for each storage category.

- **Temporary files:** Remove after processing or after a bounded retention period.
- **Incoming uploads:** Delete or isolate rejected and abandoned uploads according to policy.
- **User documents:** Retain only as long as required for the documented purpose and applicable obligations.
- **Generated reports:** Apply access restrictions and expiration rules.
- **Exports:** Restrict access, use short retention periods, and securely delete expired files.
- **Quarantine:** Define review, rejection, and deletion procedures.
- **Backups:** Follow a documented backup retention and recovery policy.

Deletion workflows should account for database references, object storage, temporary copies, and applicable backup-retention requirements.

## 6. Backup Requirements

The `backups/` directory is reserved for protected local backup workflows, not general-purpose storage.

Production database backups and sensitive document backups should preferably be stored separately from the application runtime filesystem.

Backups should have:

- Restricted access.
- Encryption where appropriate.
- Documented retention.
- Integrity verification.
- Recovery procedures.
- Periodic restoration tests.

Never commit database dumps, backup archives, or private documents to Git.

## 7. Development Practices

During local development:

- Use synthetic documents and test data.
- Keep runtime files excluded through `.gitignore`.
- Preserve intended directory structure with `.gitkeep` where needed.
- Avoid copying production personal data into development environments.
- Test upload limits, invalid file rejection, authorization failures, and deletion workflows.
- Verify that runtime files are not included in release artifacts or public deployment directories.

Ignore rules prevent ordinary Git tracking; they do not secure files on disk or remove previously committed files from Git history.

## 8. Operational Monitoring

Monitor storage operations for:

- Upload and processing failures.
- Storage-capacity exhaustion.
- Malware-scanning failures.
- Unauthorized access attempts.
- Unexpected retention or deletion failures.
- Abnormally large exports.
- Temporary-file accumulation.
- Backup failures and recovery readiness.

Logs should identify relevant operations without recording document contents, secrets, or unnecessary personal information.

## 9. Production Readiness Checklist

- [ ] Storage is outside the public web root or otherwise inaccessible to anonymous requests.
- [ ] No unrestricted static-file serving exposes private storage.
- [ ] Upload limits and file validation are enforced.
- [ ] Filenames and storage keys are generated safely.
- [ ] Quarantined files remain inaccessible until approved.
- [ ] Malware scanning is integrated where required.
- [ ] Document downloads enforce authentication and resource-level authorization.
- [ ] Sensitive storage is encrypted and access-restricted.
- [ ] Database metadata does not unnecessarily expose private storage details.
- [ ] Retention and deletion policies are implemented.
- [ ] Production backups are protected and restoration-tested.
- [ ] Runtime files and backups are excluded from Git.
- [ ] Monitoring covers storage failures and security events.

## 10. Maintenance

Keep this README synchronized with the actual storage architecture, upload pipeline, retention policies, and deployment configuration.

Before adding a new storage category, define its purpose, permitted file types, access rules, retention period, and operational requirements.

**Production principle:** A directory name, `.gitignore` rule, or storage key does not provide security by itself. Private storage requires enforced access controls, validated file handling, controlled retention, and verified deployment configuration.
