
# MedOrbits Database Queries

**Directory:** `database/queries/README.md`  
**Project:** MedOrbits — Education, Admissions, Careers & Recruitment  
**Database:** MySQL 8.0.16+  
**Storage Engine:** InnoDB  
**Purpose:** Reference documentation for reusable, parameterized SQL queries.

—

## 1. Overview

The `database/queries/` directory contains reusable SQL statements for accessing and managing MedOrbits application data.

These queries support:

- User accounts, profiles, roles, and permissions.
- Education and admission applications.
- Job listings, recruitment, and job applications.
- Audit-log retrieval and operational reporting.
- Administrative dashboards and application workflows.

Queries in this directory are database access templates. They are not API endpoints, authorization policies, migrations, or a substitute for application services.

## 3. Query File Responsibilities

| File | Responsibility |
|—|—|
| `users.sql` | User lookup, registration, profiles, account status, role assignments, and user reporting |
| `applications.sql` | Admission application creation, applicant dashboards, submission, review, and status reporting |
| `admissions.sql` | Admission-specific workflows, queues, catalogue lookups, and counselling operations |
| `jobs.sql` | Public job discovery, employer job management, job applications, and recruitment reporting |
| `audit-log.sql` | Audit-event insertion, event history, security investigations, and operational summaries |

### `users.sql`

Contains queries for authentication lookup, user profiles, registration, verification, role lookup, account lifecycle, and administrative reporting.

**Security requirements:**
- Never return password hashes through public API responses.
- Store password hashes generated by a suitable password-hashing library.
- Normalize email addresses consistently.
- Enforce role-assignment permissions in the application service.
- Protect privileged accounts against unauthorized deactivation.

### `applications.sql`

Contains queries for admission application drafts, submission, applicant-owned records, staff review, status updates, and reporting.

**Requirements:**
- Derive the applicant identity from the authenticated session or token.
- Enforce ownership in applicant-facing queries.
- Validate required fields and supporting documents before submission.
- Record status changes through the audit and status-history services.
- Preserve submitted applications according to the configured retention policy.

### `admissions.sql`

Contains queries related to admission catalogues and admission workflows, including course and college relationships, counselling queues, and admission reporting.

**Requirements:**
- Use the actual course, college, university, and counselling schema.
- Validate eligibility and admission rules in the appropriate service.
- Do not assume that a catalogue entry is eligible for admission solely because it exists.
- Keep counselling and administrative operations behind appropriate authorization checks.

### `jobs.sql`

Contains queries for published job listings, job search, employer dashboards, draft creation, publication, closure, applications, and recruitment statistics.

**Requirements:**
- Only expose published and eligible jobs through public listings.
- Verify employer ownership before editing or closing a job.
- Validate application deadlines and eligibility before accepting an application.
- Protect applicant information and resume files.
- Enforce duplicate-application rules at the database level when required.

### `audit-log.sql`

Contains queries for retrieving audit events, filtering activity, investigating failures, reviewing resource history, and producing operational summaries.

**Requirements:**
- Restrict audit-log access to authorized personnel.
- Do not record passwords, authentication tokens, secrets, or unnecessary sensitive data.
- Use consistent event identifiers and request identifiers where available.
- Protect audit records against unauthorized modification and deletion.
- Apply the organization’s retention and privacy policies.

## 4. Database Compatibility

These queries target **MySQL 8.0.16 or newer**.

Use:
- InnoDB for transactional tables.
- Foreign keys for valid relationships.
- `UNIQUE` constraints for identifiers that must not be duplicated.
- Appropriate indexes for common lookup and filtering patterns.
- `CURRENT_TIMESTAMP(3)` where millisecond precision is required.
- JSON columns only where the schema and application validate JSON values.

Do not assume compatibility with PostgreSQL. MySQL-specific syntax includes `ON DUPLICATE KEY UPDATE`, `GROUP_CONCAT`, and certain `UPDATE ... JOIN` patterns.

Check the exact server version before relying on database features.

## 5. Parameterized Query Conventions

Use placeholders (`?`) for user-supplied values and bind them through the database driver.

Example:

```javascript
const [rows] = await pool.execute(
  `SELECT public_id, name, email
   FROM users
   WHERE public_id = ?
     AND deleted_at IS NULL
   LIMIT 1`,
  [publicId]
);
```

Never concatenate user-supplied strings into SQL.

### Important parameter rules

1. Each `?` placeholder requires a corresponding bound value.
2. The number and order of values must match the query.
3. SQL identifiers, column names, and sort directions cannot be safely supplied as ordinary value parameters. Map dynamic identifiers to an explicit allowlist.
4. Validate pagination values before binding them to `LIMIT` and `OFFSET`.
5. Use separate query variants when optional filtering becomes too complex or performs poorly.
6. Verify that queries use the correct internal IDs and public identifiers.

## 6. Transactions

Use transactions for workflows that must succeed or fail together.

Typical examples:
- Creating an application and its related records.
- Submitting an application and recording its status history.
- Updating a job application and writing its audit event.
- Assigning a role and recording the administrative action.
- Consuming a single-use verification or password-reset token.

Example with a MySQL connection pool:

```javascript
async function runInTransaction(pool, callback) {
  const connection = await pool.getConnection();

  try {
    await connection.beginTransaction();

    const result = await callback(connection);

    await connection.commit();
    return result;
  } catch (error) {
    await connection.rollback();
    throw error;
  } finally {
    connection.release();
  }
}
```

Use this helper only with a compatible database driver and ensure the callback executes every transactional query through the supplied connection.

Transactions do not replace authorization, input validation, or concurrency controls.

## 7. Authorization and Data Protection

Database queries must be called through authenticated, authorized application services.

| Operation | Minimum control |
|—|—|
| Read own profile | Authenticated user and ownership check |
| Update own profile | Authenticated user and ownership condition |
| Read admission application | Applicant ownership or authorized staff access |
| Change application status | Authorized counsellor or administrator |
| Manage job listing | Verified employer ownership or authorized administrator |
| Read applicant documents | Ownership or approved recruitment permission |
| Assign privileged roles | Authorized administrative service |
| Read audit records | Restricted operational permission |

Do not treat an unguessable public UUID as authorization. Every protected resource requires a server-side permission check.

## 8. Schema Alignment

The SQL files document assumed column names and table relationships. Before integrating a query, compare it with the actual migration files.

Useful checks:

```sql
SHOW CREATE TABLE users;
SHOW CREATE TABLE applications;
SHOW CREATE TABLE courses;
SHOW CREATE TABLE colleges;
SHOW CREATE TABLE jobs;
SHOW CREATE TABLE job_applications;
SHOW CREATE TABLE roles;
SHOW CREATE TABLE user_roles;
SHOW CREATE TABLE audit_logs;
```

Some tables may not yet exist in the deployed schema. A query referencing a missing table or column will fail.

In particular, verify:
- Internal primary keys and public identifiers.
- Foreign-key relationships.
- Account and application status values.
- Soft-deletion fields such as `deleted_at`.
- Audit-log metadata types.
- Employer ownership relationships.
- Whether application-history and assignment tables exist.

Do not add columns or tables solely to satisfy a query without updating the corresponding migration and application code.

## 9. Indexing and Performance

Use indexes that match actual query patterns. Common candidates include:

- Unique indexes on public identifiers.
- Unique normalized email indexes where appropriate.
- Composite indexes for status and creation date.
- Foreign-key indexes for applicant, course, college, employer, and job relationships.
- Indexes for application status and submission date.
- Unique constraints for duplicate-prevention rules.

Before adding an index, inspect existing indexes:

```sql
SHOW INDEX FROM users;
SHOW INDEX FROM applications;
SHOW INDEX FROM jobs;
SHOW INDEX FROM job_applications;
```

Use `EXPLAIN` to examine query plans:

```sql
EXPLAIN
SELECT public_id, title
FROM jobs
WHERE status = ‘published’
ORDER BY published_at DESC
LIMIT 20;
```

Do not create duplicate indexes blindly. Index design should reflect table size, query frequency, selectivity, and write overhead.

## 10. Error Handling

The service layer should handle expected database errors explicitly.

Examples:
- Duplicate-key errors: resolve unique-constraint conflicts.
- Foreign-key violations: reject invalid relationships.
- Missing records: return the appropriate not-found response.
- Unauthorized ownership: do not disclose protected records.
- Deadlocks: retry only when the transaction is safe to retry.
- Connection failures: use bounded retries and appropriate logging.

Do not return raw SQL, database connection details, stack traces, or sensitive database errors to clients.

## 11. Testing Checklist

Before deployment, verify:

- [ ] Every query matches the current migration schema.
- [ ] Placeholder counts and parameter order are correct.
- [ ] Unauthorized users cannot access another user’s records.
- [ ] Public listings exclude unpublished or expired records.
- [ ] Duplicate registrations and applications follow the defined policy.
- [ ] Invalid status transitions are rejected.
- [ ] Transaction rollback works when any step fails.
- [ ] Soft-deleted records are handled consistently.
- [ ] Pagination is validated and bounded.
- [ ] Sensitive fields are excluded from public results.
- [ ] Required indexes exist without unnecessary duplicates.
- [ ] Audit events are written for security-sensitive actions.
- [ ] Integration tests run against a dedicated test database.

## 12. Change Management

When changing a query:

1. Inspect the associated database migration.
2. Update the query and its parameter documentation.
3. Update the calling service or repository.
4. Add or revise unit and integration tests.
5. Check query plans for high-volume operations.
6. Update this README when responsibilities or assumptions change.
7. Deploy schema changes before code that depends on them.

Avoid modifying production data through ad hoc query execution. Use reviewed migrations, controlled maintenance procedures, and backups for schema or data changes.

## 13. Production Readiness

Before production deployment:

- Remove development-only seed permissions and test credentials.
- Confirm authorization at every protected service boundary.
- Ensure sensitive data is never written to logs.
- Apply appropriate least-privilege database credentials.
- Verify backups and recovery procedures.
- Test migrations and queries in staging.
- Review retention and privacy requirements for applications, resumes, and audit records.
