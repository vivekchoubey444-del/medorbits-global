
# MedOrbits Authentication and Identity Security Policy

**File:** `docs/security/authentication.md`  
**Version:** 1.0.0  
**Classification:** Internal Security Policy  
**Applies to:** MedOrbits web application, Express APIs, PostgreSQL, administrative interfaces, document services, and background workers.

## 1. Purpose

This policy defines the requirements for establishing, verifying, maintaining, and terminating authenticated identities across MedOrbits.

Authentication MUST establish a trustworthy identity before protected operations are permitted. Authorization MUST independently determine whether that identity can access the requested resource or perform the requested action.

This policy complements `docs/security/authorization.md`.

## 2. Mandatory security requirements

All authentication implementations MUST:

- Deny protected access when authentication is missing, invalid, or expired.
- Validate credentials exclusively on trusted server-side components.
- Use approved password hashing and secure session or token management.
- Protect authentication traffic with HTTPS in production.
- Apply rate limits and abuse detection to authentication endpoints.
- Avoid account enumeration through inconsistent responses.
- Prevent credentials, tokens, and session secrets from entering logs.
- Support session invalidation and account suspension.
- Require stronger verification for sensitive operations where appropriate.
- Test authentication controls as part of CI and security review.

Authentication MUST NOT depend on frontend-only checks or client-supplied identity claims.

## 3. Identity model

MedOrbits uses the `users` table in the PostgreSQL `medorbits` schema as its core user identity record.

Relevant fields include:

| Field | Purpose |
|—|—|
| `id` | Internal database identifier |
| `public_id` | Public-facing UUID |
| `email` | Email contact and possible login identifier |
| `phone` | Phone contact and possible login identifier |
| `password_hash` | Password verifier, when password authentication is enabled |
| `role` | Application role designation |
| `account_status` | Account lifecycle status |
| `email_verified_at` | Email verification timestamp |
| `phone_verified_at` | Phone verification timestamp |
| `last_login_at` | Most recent successful login timestamp |

A public UUID is an identifier, not an authentication credential.

Email or phone verification MUST NOT automatically grant elevated privileges.

The application MUST define which login identifiers are supported, how duplicates are handled, and whether verified contact details are required for specific operations.

## 4. Password security

### 4.1 Password storage

Passwords MUST never be stored in plaintext or reversibly encrypted for routine authentication.

Use a maintained password-hashing implementation, preferably **Argon2id**. A suitable alternative is a properly configured bcrypt implementation when Argon2id is unavailable.

Parameters MUST be selected according to current security guidance and the deployment’s performance constraints, then periodically reviewed.

Password hashes MUST be generated and verified through a vetted library. Custom password-hashing algorithms MUST NOT be implemented.

The `password_hash` column MUST contain only the encoded verifier generated by the selected password-hashing library.

### 4.2 Password requirements

The application SHOULD:

- Permit long passwords and passphrases.
- Support password managers and pasting.
- Reject commonly compromised passwords using an appropriate blocklist.
- Avoid arbitrary periodic password changes without evidence of compromise.
- Avoid unnecessary character-composition rules that encourage predictable passwords.
- Enforce reasonable maximum input lengths to prevent resource exhaustion.
- Avoid silently truncating passwords.

Password length, maximum input size, and any composition policy MUST be documented consistently across registration, login, and password-reset flows.

### 4.3 Password verification

Login handlers MUST:

1. Validate the request structure.
2. Apply rate limiting and abuse controls.
3. Find the candidate account using a normalized identifier.
4. Verify the password with the approved password-hashing library.
5. Check account status and required verification state.
6. Establish a fresh authenticated session only after successful verification.
7. Record appropriate security events without logging the password.

For unknown accounts, implementations SHOULD perform a comparable password-verification workload where practical to reduce timing-based account enumeration.

Client-facing failures SHOULD use generic messages such as:

`Invalid email/phone or password.`

Do not disclose whether a particular account exists, is disabled, or has an incorrect password.

## 5. Registration and contact verification

Registration MUST validate user input on the server and enforce uniqueness rules for supported identifiers.

Email addresses SHOULD be normalized consistently for lookup and uniqueness. Phone numbers SHOULD be normalized to a documented format, such as E.164, where applicable.

Verification tokens MUST be:

- Cryptographically random.
- Bound to the intended account and purpose.
- Short-lived.
- Single-use.
- Invalidated after successful verification or expiration.
- Stored securely, preferably as a hash when practical.

Verification endpoints MUST be rate-limited.

The application MUST NOT mark an email or phone as verified merely because a user supplied it in a registration request.

Account activation policies MUST explicitly define the treatment of pending accounts.

## 6. Login and brute-force protection

Login, registration, verification, password-reset, and other authentication endpoints MUST use rate limiting appropriate to their risk.

Controls SHOULD include:

- Per-account or per-identifier throttling.
- Per-IP and broader abuse detection.
- Progressive delays or temporary restrictions where appropriate.
- Monitoring for credential stuffing and password spraying.
- CAPTCHA or additional verification when justified by abuse signals.
- Safe handling of distributed attacks and proxy networks.

Do not permanently lock accounts solely because an attacker repeatedly submits invalid passwords. This can create a denial-of-service mechanism against legitimate users.

Rate limits MUST account for deployment architecture. When multiple application instances are running, use a shared rate-limit store where necessary rather than relying exclusively on process-local memory.

Authentication failures SHOULD be logged in a privacy-conscious way. Logs MUST NOT contain submitted passwords, raw reset tokens, access tokens, or session identifiers.

## 7. Session management

For browser-based authentication, MedOrbits SHOULD prefer a secure server-managed session unless a reviewed token-based architecture is required.

### 7.1 Cookie controls

Production session cookies MUST use:

- `HttpOnly`
- `Secure`
- An appropriate `SameSite` setting
- A restrictive cookie path and domain configuration where practical

Session identifiers MUST be unpredictable and generated by a trusted session implementation.

The session cookie MUST NOT contain a plaintext password or sensitive personal data.

### 7.2 Session lifecycle

The application MUST:

- Rotate session identifiers after successful authentication.
- Rotate or revalidate sessions after significant privilege changes.
- Invalidate sessions after logout.
- Apply idle and absolute expiration policies.
- Revoke sessions following account suspension or confirmed compromise.
- Prevent concurrent requests from restoring invalidated sessions.
- Avoid accepting expired or revoked sessions.

Session expiration values MUST be selected according to risk and documented configuration. High-risk administrative sessions SHOULD be shorter-lived than ordinary low-risk sessions.

### 7.3 Session storage

Production deployments MUST NOT use an in-memory development session store for a multi-instance or restart-sensitive environment.

Use a supported shared session store when server-side sessions are required across multiple instances.

Session storage MUST be protected by appropriate access controls and MUST NOT expose session contents to unauthorized users.

## 8. CSRF and browser security

Cookie-authenticated state-changing endpoints MUST use appropriate cross-site request forgery protection.

Depending on the architecture, controls SHOULD include:

- CSRF tokens.
- `SameSite` cookie restrictions.
- Origin or Referer validation where appropriate.
- Strict content-type and request-method handling.

CORS is not a substitute for CSRF protection.

GET and other safe HTTP methods MUST NOT perform state-changing operations.

## 9. Token-based authentication

If MedOrbits uses bearer tokens, the implementation MUST validate all applicable claims and cryptographic properties.

For signed tokens, validate:

- Signature and explicitly permitted algorithm.
- Issuer (`iss`).
- Audience (`aud`).
- Expiration (`exp`).
- Not-before (`nbf`), when present.
- Subject (`sub`) and required application-specific claims.

Do not accept an algorithm selected solely from untrusted token input.

Access tokens SHOULD be short-lived. Refresh tokens MUST be protected, rotated or otherwise controlled, and revocable according to the token lifecycle design.

Logout and account suspension MUST have a defined effect on token validity. If immediate revocation is required, the architecture MUST include a suitable server-side mechanism.

Tokens MUST NOT be placed in URLs or written to application logs.

Browser storage choices MUST be evaluated against XSS and CSRF risks. Do not assume that storing a token in local storage is safe merely because the application uses HTTPS.

## 10. Password reset and account recovery

Password recovery MUST NOT weaken the normal authentication process.

The application MUST:

1. Return generic responses that do not reveal account existence.
2. Rate-limit reset requests.
3. Generate cryptographically random, short-lived, single-use reset tokens.
4. Bind each token to the intended account and recovery purpose.
5. Store tokens securely, preferably as hashes.
6. Invalidate a token after successful use.
7. Prevent reuse and concurrent replay.
8. Notify the account holder after a password change.
9. Revoke existing sessions or require reauthentication according to the documented risk policy.

Reset links MUST use a configured trusted origin. Do not construct them from an untrusted `Host` header.

Support staff MUST NOT ask users to disclose passwords, one-time codes, or reset tokens.

## 11. Multi-factor authentication

Multi-factor authentication SHOULD be available for administrative and other high-risk accounts.

Where enabled, MFA MUST be enforced server-side and MUST NOT be bypassable through alternate login, recovery, API, or legacy endpoints.

The implementation SHOULD define:

- Enrollment and verification.
- Recovery codes and their secure storage.
- Device replacement and recovery procedures.
- MFA reset authorization.
- Session behavior following factor changes.
- Alerts for suspicious changes.

Recovery mechanisms MUST receive security protections appropriate to the authentication method they can replace.

## 12. Account lifecycle and status enforcement

The application MUST enforce the account states defined by the MedOrbits database schema:

- `pending`
- `active`
- `suspended`
- `disabled`
- `deleted`

The authentication service MUST explicitly define which states may authenticate and which capabilities each state permits.

Suspended and disabled accounts MUST be denied ordinary interactive authentication. Pending accounts MUST follow the documented activation policy.

Deleted accounts MUST not be reactivated implicitly by registration or identifier reuse.

Account suspension and confirmed compromise MUST trigger the documented session and token revocation process.

## 13. Administrative and service authentication

Administrative access MUST require explicit authorization in addition to authentication.

High-risk administrative operations SHOULD require MFA or recent reauthentication.

Background workers and service-to-service integrations MUST use dedicated identities and narrowly scoped credentials.

Service credentials MUST:

- Be generated securely.
- Be stored in a secret manager or protected environment configuration.
- Have limited permissions and lifetimes where practical.
- Be rotated according to documented risk requirements.
- Be revoked when compromised or no longer required.
- Never be committed to source control.

Interactive user credentials MUST NOT be reused as service credentials.

## 14. PostgreSQL and application integration

The database stores password verifiers and account status, but authentication decisions MUST be implemented in trusted application code.

Database access MUST use parameterized queries. Database credentials MUST NOT be exposed to browsers.

The application MUST:

- Verify passwords using the approved password-hashing library.
- Avoid returning `password_hash` in API responses.
- Restrict database permissions for authentication data.
- Update `last_login_at` only after successful authentication.
- Set verification timestamps only after successful verification.
- Avoid relying on database role fields as the sole authorization control.

The application SHOULD separate public user profile responses from internal authentication records.

## 15. Express implementation requirements

Authentication routes SHOULD be separated from general application routes and use dedicated validation, authentication, and rate-limiting middleware.

Example route structure:

```javascript
router.post(
  “/login”,
  loginRateLimiter,
  validateLoginRequest,
  authController.login
);

router.post(
  “/logout”,
  authenticate,
  authController.logout
);

router.post(
  “/password/forgot”,
  passwordResetRateLimiter,
  validateResetRequest,
  authController.requestPasswordReset
);

router.post(
  “/password/reset”,
  passwordResetRateLimiter,
  validatePasswordReset,
  authController.resetPassword
);
```

This is an illustrative route structure. The referenced middleware and controllers must exist and implement the required controls before these routes are enabled.

Do not create placeholder authentication middleware that always allows access.

## 16. Authentication logging and monitoring

Record appropriate authentication events, including:

- Successful login.
- Failed login.
- Logout.
- Password changes and recovery.
- Contact verification.
- MFA enrollment, removal, and recovery.
- Session revocation.
- Suspicious authentication patterns.
- Account suspension and reactivation.

Audit records SHOULD include timestamps, event type, outcome, a suitable account reference, and request correlation identifiers.

Logs MUST NOT contain passwords, raw tokens, session cookies, reset tokens, MFA secrets, or other authentication secrets.

Monitoring SHOULD alert on suspicious patterns, including credential stuffing, repeated recovery requests, unexpected privileged logins, and unusual session activity.

## 17. Error handling and privacy

Authentication responses MUST NOT reveal password hashes, internal credentials, signing keys, stack traces, database errors, or unnecessary account information.

Return generic public errors and record diagnostic details in restricted logs.

Authentication data MUST be retained only as long as needed for documented security and operational purposes, subject to applicable legal requirements.

## 18. Automated testing

CI MUST test at least the following:

- Valid and invalid login attempts.
- Missing and malformed credentials.
- Unknown account behavior.
- Password verification and hash storage.
- Email and phone verification.
- Expired, invalid, and reused recovery tokens.
- Session fixation and session rotation.
- Logout and session invalidation.
- Expired and revoked bearer tokens, if used.
- Suspended and disabled account behavior.
- Rate-limit enforcement.
- CSRF protections for cookie-authenticated mutations.
- MFA enforcement, if implemented.
- Sensitive-field redaction.
- Concurrent password-reset attempts.
- Authorization after authentication.

Tests MUST cover both successful and denied paths.

## 19. Production deployment checklist

- [ ] HTTPS is enforced.
- [ ] Password hashing uses a maintained, appropriately configured library.
- [ ] Authentication endpoints have rate limits.
- [ ] Login errors avoid account enumeration.
- [ ] Session or token expiration and revocation are implemented.
- [ ] Cookie settings are secure for the production architecture.
- [ ] CSRF protection is implemented where required.
- [ ] Password recovery uses single-use, expiring tokens.
- [ ] MFA is configured for high-risk accounts where required.
- [ ] Account status is enforced consistently.
- [ ] Authentication secrets are excluded from logs and source control.
- [ ] Database access follows least privilege.
- [ ] Authentication tests run in CI.
- [ ] Recovery and incident response procedures are documented.

## 20. Incident response

If credentials or sessions are suspected to be compromised:

1. Revoke affected sessions, refresh tokens, and credentials.
2. Restrict affected accounts or authentication capabilities as necessary.
3. Preserve relevant security logs.
4. Assess affected accounts and potentially exposed data.
5. Reset credentials using the approved recovery process.
6. Identify and remediate the root cause.
7. Add regression tests and verify remediation.
8. Follow applicable notification and reporting obligations.

## 21. Policy maintenance

The security owner MUST review this policy periodically and whenever authentication methods, session architecture, account recovery, or identity storage change.

Changes MUST be reviewed and tested before production deployment.

This document defines security requirements. It does not itself implement, test, or certify the authentication system.

**End of policy**
