
# Lead API

**Project:** MedOrbits  
**Endpoint:** `/api/lead`  
**Runtime:** Node.js  
**Framework:** Next.js App Router  
**Database:** PostgreSQL  
**Method:** `POST`

## 1. Purpose

The Lead API receives course-admission enquiries from the MedOrbits website, validates submitted data, and stores accepted leads in the PostgreSQL `leads` table.

Typical uses include:

- MBBS and medical admission enquiries
- Course and college guidance requests
- Study-abroad enquiries
- Education consultancy contact forms

## 2. Endpoint

```http
POST /api/lead
Content-Type: application/json
```

The route implementation must be located at:

```text
app/
└── api/
    └── lead/
        ├── route.js
        ├── route.test.js
        └── README.md
```

Next.js App Router requires the filename `route.js`, not `routes.js`.

## 3. Request format

Example request body:

```json
{
  “name”: “Example User”,
  “email”: “user@example.com”,
  “phone”: “+919876543210”,
  “course”: “MBBS”,
  “message”: “Please provide information about admission.”,
  “website”: “”
}
```

The `website` field is an optional honeypot field intended to help identify automated submissions. Normal users should leave it empty.

### Field requirements

| Field | Requirement |
|—|—|
| `name` | Required; maximum 120 characters |
| `email` | Required; maximum 254 characters; basic email validation |
| `phone` | Optional; maximum 30 characters; validated when supplied |
| `course` | Required; maximum 160 characters |
| `message` | Optional; maximum 5,000 characters |
| `website` | Optional honeypot field |

The route should reject malformed JSON, invalid field types, missing required fields, invalid email addresses, and oversized request bodies.

## 4. Success response

HTTP status:

```http
201 Created
```

Example response:

```json
{
  “success”: true,
  “message”: “Lead submitted successfully.”,
  “id”: 123
}
```

The returned `id` is generated by the database. Its exact JSON type depends on how the route serializes the database value.

## 5. Error responses

| HTTP status | Meaning |
|—|—|
| `400` | Invalid JSON or invalid input |
| `403` | Request origin is not allowed |
| `405` | HTTP method is not supported |
| `413` | Request body is too large |
| `415` | Unsupported content type |
| `503` | Database configuration or submission failure |

Example validation response:

```json
{
  “success”: false,
  “error”: “Invalid request.”
}
```

Exact error messages depend on the implementation in `route.js`.

## 6. PostgreSQL setup

Install the PostgreSQL driver from the repository root:

```bash
npm install pg
```

Create the table if it does not already exist:

```sql
CREATE TABLE IF NOT EXISTS leads (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    email VARCHAR(254) NOT NULL,
    phone VARCHAR(30),
    course VARCHAR(160) NOT NULL,
    message TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_leads_created_at
    ON leads (created_at DESC);
```

Run this SQL using your PostgreSQL database administration tool or migration process.

## 7. Environment variables

Configure these variables in your local environment and deployment platform:

```dotenv
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DATABASE
ALLOWED_ORIGINS=https://example.com,https://www.example.com
```

Replace the example database connection and domain names with your actual values.

- `DATABASE_URL` must point to the PostgreSQL database.
- `ALLOWED_ORIGINS` should contain the exact trusted website origins, separated by commas.
- Keep database credentials in environment variables, never in source code.
- Do not commit `.env` files containing real credentials.

If `ALLOWED_ORIGINS` is empty and the route permits all origins, configure the allowlist before exposing the endpoint publicly.

## 8. Frontend integration

Example browser request:

```javascript
async function submitLead(lead) {
  const response = await fetch(“/api/lead”, {
    method: “POST”,
    headers: {
      “Content-Type”: “application/json”
    },
    body: JSON.stringify(lead)
  });

  const result = await response.json().catch(() => ({
    success: false,
    error: “The server returned an invalid response.”
  }));

  if (!response.ok) {
    throw new Error(result.error || “Unable to submit your enquiry.”);
  }

  return result;
}
```

Example usage:

```javascript
try {
  const result = await submitLead({
    name: “Example User”,
    email: “user@example.com”,
    phone: “+919876543210”,
    course: “MBBS”,
    message: “Please contact me about admissions.”
  });

  console.log(“Lead submitted:”, result.id);
} catch (error) {
  console.error(error.message);
}
```

Display a clear success or failure message to the user. Do not log sensitive enquiry details unnecessarily.

## 10. Security requirements

Before deploying this endpoint to production:

- Enforce request-size limits and server-side validation.
- Use parameterized SQL queries; never concatenate user input into SQL.
- Configure a strict origin allowlist.
- Add rate limiting and abuse protection, such as CAPTCHA where appropriate.
- Consider email verification or other lead-verification controls.
- Restrict database privileges to only the operations the application needs.
- Keep production credentials and logs protected.
- Define a retention and deletion policy for personal information.
- Apply appropriate privacy notices and consent requirements.
- Monitor repeated failures and suspicious traffic without logging unnecessary personal data.

**Important:** CORS and origin checks are not authentication. A public endpoint can still be called directly by scripts or other HTTP clients. Use rate limiting and additional controls to reduce spam and abuse.
